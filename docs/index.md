## 任务状态生命周期

**项目状态**维护跨任务的事实与约束；**任务状态**保存本次用户意图与执行偏好，供 fresh subagent、compact 后或接管的主控快速收敛，不是第二份长计划。

1. **建立唯一文件**：主控在任务开始时创建 `.plan/<任务>/task-state.md`。已有计划放在其它目录时原地使用同名文件，不迁移、不复制；在 `AGENTS.md` 登记当前任务入口，便于恢复时定位。本轮入口是 [Rust 后端修复 task state](reports/2026-09-22-rust-electron-rewrite/task-state.md)；尚未建立状态的旧任务，在再次接手时补齐，不凭空补写历史。
2. **四项核心内容**：用户意图与不可丢失的偏好；实现所需专项知识/来源与关键边界；当前进度和验收结论；当前问题、待决策项与下一步。另附计划/证据链接及当前执行位置。建议控制在约 60–100 行，小任务更短；不复制日志、工具流水或整套计划。
3. **唯一写入权**：只有用户和主 Agent 可修改。subagent 开始时读取，变化通过报告或 supervisor 提请主控更新，不得自行编辑、创建替代版或在 worktree 同步可写副本。
4. **读取与更新时机**：开始、恢复/compact 后、委派前先读；用户调整偏好、关键决策、阶段验收、阻断或下一步改变后由主控更新。brief 给出 canonical 文件绝对路径、相关计划与本次范围；主控应在交还控制/可能 compact 前补齐重要变化，不为每个工具调用记流水。
5. **冲突与证据**：最新用户决定及时写入 task state；计划与状态不符时由主控核实同步，叶子先询问，不自行挑选。任务偏好不豁免项目硬边界；未核实、已复现、worker 报告和主控验收须明确区分。
6. **收尾与升格**：任务完成后，主控把经验证且可复用的经验提炼到 `docs/lessons/`，必要时同步架构/参考文档；task state 标记完成，链接最终验收和经验总结，并同步当前任务入口，避免旧任务继续被当作进行中。失败教训可以升格，但未解决方案不能写成成功实现。

## 维护规则

- 项目当前事实在架构地图与参考文档维护；长期目标和未落实决策在设计文档维护；单次任务的意图/执行偏好与最新门禁在 task state 维护。经验文档总结可复用结论，不复制三者全文。代码变化时，同一个改动中更新对应说明。
- 文档记录责任边界、关键路径和失败语义。参数全集看 `bdt <子命令> --help`，HTTP 字段看 `/openapi.json` 与路由/模型，避免手抄大份 schema。
- 保持目录精简。先合并到现有主题，确有独立读者和长期维护责任再讨论拆篇；每任务必备的短 task state 除外，不为每次任务新增设计稿或验收长文。
- 实验数据、截图、测试日志存本仓库 `tmp/`；旧 docs 已移除，历史依据从 Git 历史查看，不维护第二套归档知识库。
- 工作台界面与交互只在 `web/src` 及其行为测试里维护；本轮界面定稿用过的静态设计稿 `web/design/` 已删除，不再重建或另建第二份界面原型。
- 验证命令见 [检查出口](guide/cli.md)。文档构建只能检查结构/链接；架构结论仍要追到代码与行为测试。

这套结构采用 [Harness engineering](https://openai.com/index/harness-engineering/) 的短入口、仓库知识与反馈检查思路；全局地图参考 [ARCHITECTURE.md 建议](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html)。本项目按实际规模保留少量文件。
