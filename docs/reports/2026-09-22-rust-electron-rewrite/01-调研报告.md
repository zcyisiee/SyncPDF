# SyncPDF 重写调研报告

日期：2026-09-22。范围：把当前 Python 版（BabelDOC fork + `bdt` 七阶段 + FastAPI serve + React 工作台）重写为 **SyncPDF**：Rust 引擎 + Electron 前端，输出方式从「bbox 贴片 + XeLaTeX」改为「内容流改写」。

本报告是四份细节调研的汇总。细节与证据见 `research/` 目录：

| 文件 | 内容 |
|---|---|
| `research/01-current-project-audit.md` | 当前项目全量审计，18 条必留规约，14 条可弃包袱 |
| `research/02-hjfy-engine-deep-dive.md` | hjfy 引擎逆向：IR、回写、字体、排版、协议、事件 |

| `research/04-performance-baseline.md` | 现版性能基线、17 条贴片模型缺陷、重写目标数字 |

## 1. 结论

1. 现版最慢的可控环节是 build 与流式编译。根因是 xelatex 进程开销，不是算法。
2. 贴片覆盖模型有 17 条固有缺陷。其中 7 条在内容流改写下自然消失，3 条部分消失。
3. hjfy 已经证明「操作级补丁 + 追加隔离流 + 子集 CID 字体」在 Rust 生态可行。方案照搬，不做原创设计。
4. 前端不 fork Code-OSS。自建 Electron + React，复用 VSCode 视觉系统与分栏布局。
5. 引擎以 sidecar 进程 + stdin/stdout JSONL 接入 Electron。不用 napi-rs。

## 2. 重写动机：实测数字

### 2.1 端到端分阶段耗时（健康样本 up-vns，12 页，169 段）

| 阶段 | 耗时 | 性质 |
|---|---|---|
| parse | 26.1s（MinerU 缓存命中）/ 63.8s（未命中，云端轮询 37s） | 本地部分 ~17s 可优化 |
| translate | 219–242s | 外部 LLM，重写不改变 |
| apply | 5.2s | 纯逻辑 |
| build | 52s | 18 次 xelatex，106 补丁两遍 |
| check | 160s | 黑盒，无细分证据 |
| review / report | 短 | — |
| 合计 | ~7.5 min | — |

其他样本：up-trc 27 页 parse 20.5 / translate 540.7 / apply 6.3 / build 57.7 / check 54.9s。up-2602 58 页 build 修复前 1377.8s。

### 2.2 xelatex 固定开销

| 项 | 数字 |
|---|---|
| 单次 xelatex | ~0.85s（并发下 1.6s） |
| 进程启动 + 导言区占比 | ~2/3 |
| 批梯队摊薄后 | 97ms/段 |
| 流式单块 p50 / 尾延 | 4.6s / 14.2s |

结论：build 的成本主要是进程与导言区，不是排版本身。换掉 xelatex 就消掉这一层。

### 2.3 体积与资产

| 项 | 数字 |
|---|---|
| conda 环境 | 1.1GB |
| TeX 发行版 | 10GB |
| 缓存 | 2.9GB |
| 导出膨胀 | 1.6MB → 23.2MB（14.5×，对象 2718 → 14514） |
| 预览资产 | 6.9MB → 177MB 无上限；376 目录 30.3GB |
| 前端预览重载 | 94% 为无效重载 |

### 2.4 check 阶段的空白

check 160s 在调研中没有找到任何细分证据。建议在 M0 之前对现版 check 补一次插桩测量。重写决策不依赖这个数字，但它决定 Rust 版是否需要专门的校验加速设计。

## 4. 必须保留的行为规约（18 条）

来源 `research/01-current-project-audit.md` §7.1。Rust 版每条都要有对应测试。

| # | 规约 | Rust 版落点 |
|---|---|---|
| 1 | 段落身份协议：确定性 id、模型不得重编号、id 集合严格匹配 | `syncpdf-core` ParagraphId + validator |
| 2 | 占位符多重集协议：丢失 / 幻觉 = 违规，顺序自由 | validator 的 placeholder_count / unknown_placeholder |
| 3 | 确定性修复 + 可观察回退：fallback_ids / empty_ids 留证据 | issue 事件 + 报告 |
| 4 | 续跑哈希：每阶段输入 sha256，stale 不静默复用 | 阶段缓存键 = 输入哈希 |
| 5 | revision 单调 +1，base_revision 乐观并发 409 | 草稿存储 |
| 6 | 坐标系约定：服务端只标 coord_system，前端 pdfToScreen 唯一换算点 | 引擎输出 PDF 用户空间坐标；前端 `viewport.convertToViewportRectangle` |
| 7 | 链接四级定位 + 注记原地更新 + 审计 | 显式 char id 取代 pickle `id()` |
| 8 | 布局覆盖率门禁 ≤0.5% | layout 阶段门禁 |
| 9 | not_replaced 是落定不是失败 | 段落状态枚举 |
| 10 | 选档一致性：快路与逐档必须同结果 | 排版 fit 单一实现 |
| 11 | 浮动三级顺序 + 跨页门禁 + 并发账本 | 改写后浮动语义简化，保留门禁 |
| 12 | 事件语义：数字游标续传、null vs []、不编造进度 | JSONL 事件 seq |
| 13 | 译文侧识别三态，绝不用源侧冒充 | 同上 |
| 14 | 资产内容寻址 + 共享资产保留 | 存储层 |
| 15 | 安全边界：密钥不进 argv、不落日志、凭据 0600 | 见技术路径 §11 |
| 16 | 公式五级分类，不猜 | 原子（atom）机制 |
| 17 | 能力探测降级，任务不失败 | 字体 / 模型缺失走降级 |
| 18 | 双语对照输出 | M4 |

## 6. hjfy 引擎的可借鉴之处

| 借鉴项 | 要点 | 处理 |
|---|---|---|
| 管线分层 | pdfium+lopdf 解析 → DisplayItem/Glyph IR → ONNX 布局 → 段落 → 翻译单元 → LLM → 16 码校验 → 排版 → 补丁回写 → 双校验 → 原子落盘 | 照搬 |
| Glyph 溯源 | GlyphSource(element_index, string_operand_range, decoded_code_range) | 照搬，作为 char id 基础 |
| 翻译协议 | 受限 HTML `<span data-style>` + `{{KEEP_N}}` 原子 + 前后文 / 术语注入 | 与现版锚点 Markdown 合并，见技术路径 §5 |
| 16 条校验码 | invalid_markup … residual_japanese | 照搬，加现版 fallback 语义 |
| 失败拆分 | 校验失败按 span / 原子边界二分重试 | 照搬 |
| 缓存 | SQLite `translations` 三元组主键 WITHOUT ROWID + WAL | 照搬 |
| 回写 | `((stream_obj_id,gen),op_index)` 补丁键；GlyphIdentity 完整命中才删；Form XObject 克隆改名再补丁；译文追加隔离 `q…Q` 流 | 照搬 |
| 字体 | Type0/CIDFontType2 + subsetter 保 gid + `/CIDToGIDMap /Identity` + 自定义 cidchar CMap + ToUnicode + /W | 照搬 |
| 自校验 | 生成后重新解析：图形栈平衡、CID 合法、链接矩形守恒、签名页拒绝；再 qpdf --check | 照搬，qpdf 可选 |
| 排版 | 缩放阶梯、邻接间隙加宽、碰撞、竖排、首字下沉、斜体剪切 | 首发做阶梯 + 加宽 + 碰撞；竖排 / 首字下沉后置 |
| 事件 | JSONL protocol_version、stage 序列、stdin EOF = 取消 | 照搬 |

hjfy 未定论 9 项（缩放阶梯精确步序、HJFYFM 用途等）不阻塞设计，M0 实测决定。

## 7. 技术栈选型

| 层 | 选定 | 否决与理由 |
|---|---|---|
| PDF 解析 / 字形几何 / 渲染 | pdfium-render 0.9.4 | mupdf（AGPL）、pdf-extract（太弱） |
| 内容流回写 | 自写 Op 过滤器（参考 pdf-rs `Op`，递归 Form XObject + CTM）+ pdf-writer 0.15.0；lopdf 0.45 对象级备选 | krilla 直接改写（只创建不改） |
| 字体 | skrifa 0.47 + harfrust 0.13.3 + subsetter 0.2.6 + fontdb 0.24 | rustybuzz（停更）、ttf-parser（维护模式） |
| 断行 / 禁则 | icu_segmenter 2.3.0 Strict + hypher 0.1.8 | unicode-linebreak（被覆盖） |
| 图像 | image 0.25 + tiny-skia 0.12 | — |
| ONNX | ort `=2.0.0-rc.13`（coreml feature） | tract、burn |
| 布局模型 | PP-DocLayoutV2 官方 ONNX 起步 → V3 升级；经 oar-ocr 0.9.2 或只用其前后处理 | DocLayout-YOLO（AGPL 停更）、内嵌 MinerU |
| OCR | PP-OCRv6 small | — |
| LLM 客户端 | genai 0.6.5；备选 reqwest 0.13 rustls + eventsource-stream | rig、社区 Anthropic crate |
| 持久化 | rusqlite 0.40 bundled + serde + ciborium + zstd 0.14 | sqlx |
| 进程模型 | Electron 主进程 `child_process.spawn` sidecar + JSONL | napi-rs、utilityProcess |
| 并发 | tokio 1.53 + rayon 1.12；pdfium 收敛单线程 | — |
| 前端路线 | 自建 Electron + React + VSCode 视觉系统：allotment 1.20.5 + `--vscode-*` token + @vscode/codicons + @vscode-elements/elements 2.5.1 | fork Code-OSS、Theia |
| Electron 工具链 | electron 44.4.3 + electron-vite 5.0.0 + electron-builder 26.15.3 + electron-updater 6.8.9 | Forge |
| PDF 预览 | pdfjs-dist 6.3.289 裸 API | react-pdf 11 |
| 段落编辑器 | 普通 textarea / contenteditable | Monaco（过重） |

模型提供方默认 OpenAI 兼容端点，Anthropic Messages 第二。

## 8. 风险表

| 风险 | 等级 | 缓解 |
|---|---|---|
| ort 长期停在 2.0 rc | 中 | 钉死 `=2.0.0-rc.13`；近两年无破坏性变更 |
| pdfium-render 全局锁阻碍页级并行 | 中 | pdfium 调用收敛到专用单线程队列；推理 / 排版 / LLM 并行不受影响 |
| harfrust 年轻 | 低 | HarfBuzz 官方背书；API 近似 rustybuzz 可临时回退 |
| oar-ocr 单维护者 0.x | 中 | 只借前后处理代码，自管 ort session 与模型分发 |
| PP-DocLayoutV3 无官方 ONNX、142MB | 中 | V2 起步；V3 自转 + FP16 |
| 内容流改写在复杂 PDF 上的未知情况（签名、加密、Pattern、Type3） | 高 | M0 spike 用三份真实 PDF 早验证；签名页拒绝处理；不可处理页降级为不译 |
| 排版质量（CJK 断行、对齐）需长期打磨 | 中 | 首发只保证「不溢出、不重叠」；质量项列入 M4 |
| check 阶段 160s 原因不明 | 低 | 重写前插桩 |
| 前端视觉还原度 | 低 | 自建路线 2–4 周达 70–85% |
