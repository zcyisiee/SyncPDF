## 结论

Rust 内容流删除、字体嵌入和译文内容流写入已接通，实际路径不调用 LaTeX。但输入解析、输出字号、流式交付和失败门禁存在阻断问题，不能认定恢复了 hjfy 可交付的翻译引擎。

## 阻断问题（按修复优先级）

### P0：PDF 写入字号重复缩放

`engine/crates/syncpdf-pdf/src/writer.rs:169-199`：正常 `scale_x == 1` 时，`Tf` 使用 `size`，同时 `Tm` 的 a/d 也使用 `size`。实际文字缩放变成字号平方；应只在其中一层施加字号。

真实译文和 fake:cjk 输出均出现巨大文字、严重重叠。证据：`tmp/accept-2106/real-page1.png`、`benchmark-page1.png`。这是内容流写入错误，不能归因于模型翻译质量。

### P0：源解析与布局无法可靠提供正文

- 398 条 `bind_degraded`，例如首页 `codes=71 chars=72`。`bind.rs` 对数量不等仍以前缀按序配对，无法保障字符与源字节正确对应。
- 23/23 页触发 `coverage_gap`；多页未覆盖比例在 30% 左右。具体布局坐标/模型预处理根因尚未确认，不应先武断指定修复。
- 首页抽段有 `HandcraftedBackdoorsinDeepNeuralNetworks`（空格丢失）、`mparedtopoisoning,andweshowitcan norremo`（残缺）、侧边 arXiv 编号混入正文并串行错乱。
- 证据：`inspect-page1.txt`、`events.jsonl`，原文对照 `source-page1.png`。

需先建立源文本/阅读序/布局叠加验收，再重新调用模型。模型实际返回的中文已受坏输入影响。

### P0：快照重放包含尚未删除原文的页面

`run.rs::writeback_page` 只删除当前就绪页原字形，但把整个 `typeset_by_page` 交给 `render_snapshot`，其中包含其他尚未就绪页已排好的段落。此次只发布第 3 页 ready 时，首页已出现译文叠加在未删原文上。应限制快照重放范围，或实现段落删除/写入一致的事务。

### P1：所谓流式翻译实际是整片收完再交付

`engine/crates/syncpdf-translate/src/translator.rs::run_prompt` 先在 delta 回调里收集 `raw`，等待 `translator.translate(...).await` 完成后，才验证并调用 `on_block`。因此 pi 传输流式不等于 pipeline 段落流式。

此外默认提示词上限 60,000 字符，超限按页拆片；本次已观察到后续 pi 子进程，不能宣称整篇严格单次 one-shot。需明确支持的文档大小与拆片策略，并用慢速 delta 测试证明响应结束前可产生段落与页预览。

### P1：错误不阻止成功状态

- `validate_output` 遇到 self_check error 只发 issue；主流程仍发布 `ok:true`。
- `writeback_page` 的删除/保存错误仅打日志，不向主流程传播。
- CLI translate 遇到 pipeline error 仍返回 `Ok(())`，进程退出状态不足以判断成功。
- fake 跑出现 256 次溢出、256 次字号下限与 self_check issue，仍返回成功。不能把事件结束或测试全绿当成视觉质量通过。
